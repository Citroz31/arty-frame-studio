## Défauts corrigés dans cette revue

| Problème observé | Comportement corrigé |
| --- | --- |
| Les actions principales étaient sous la zone visible à la taille par défaut. | Barre fixe Envoyer / Arrêter / Chronogramme ; seuls les paramètres défilent. |
| Une compilation, même distante, désactivait STOP et le suivi UART. | La compilation laisse fonctionner les commandes et le suivi. Le chargement JTAG bloque les commandes et ferme la session UART. |
| Le test LED réservait la liaison pendant environ 2,5 secondes, même pendant une émission. | Le bouton est désactivé pendant une émission pour laisser l'arrêt disponible. Le protocole LED reste inchangé. |
| La démo employait des libellés pouvant évoquer une confirmation matérielle. | Badge Simulation, identité simulée, bouton Simuler les LED et journal explicitement local. |
| Des indications supposaient toujours 200 MHz, 2,5 ns et le brochage de référence. | Pas temporel calculé depuis le cœur ; configuration connue affichée par identifiant. Un firmware inconnu demande de consulter sa configuration, sans inventer ses broches. |
| Une compilation locale ne changeait pas le fichier proposé au chargeur Windows. | Le résultat est sélectionné dans les deux champs de chargement ; le bouton Utiliser le firmware fourni rétablit la référence. |
| Un manifeste avec Fmax NaN pouvait être accepté sans rapport de timing. | Valeurs numériques finies exigées ; contrôle croisé de la cible, du SHA256, de la configuration, du commit source, du timing et du reçu de compilation. |
| Un firmware téléchargé n'était plus contrôlé par son manifeste au chargement natif. | Le même validateur est rappelé avant JTAG pour les fichiers accompagnés d'un manifeste. |
| La limite ZIP s'appliquait à chaque fichier, avec des dossiers partiels laissés après erreur. | Limite cumulée de 64 Mio, doublons refusés, extraction temporaire et déplacement dans `builds/` seulement après validation. |
| L'arrondi XDC à trois décimales relâchait légèrement certaines contraintes : 150 MHz devenait environ 149,9925 MHz. | Période calculée précisément et arrondie vers une contrainte plus stricte ; la référence à 200 MHz conserve son XDC exact. |
| Un timeout INFO était présenté comme une absence de réponse PING. | Message distinct : PING reçu, identification INFO incomplète. Une perte de liaison efface l'identité et les voyants. |

## Disposition de l'interface

**Pilotage** regroupe connexion, valeur de trame et séquence temporelle.
Les paramètres occupent deux colonnes sur une fenêtre large et une colonne
sur une petite fenêtre. Les actions restent visibles dans les deux cas.
Les profils et la base de temps sont repliables.

**FPGA** propose d'abord le chargement du `.bit` fourni sous Windows,
puis le retour vers Pilotage pour connecter le port et vérifier les LED.
Les paramètres JTAG, la personnalisation et les outils locaux sont repliables.
Les chemins de fichiers disposent d'un bouton Parcourir dans l'application
de bureau. Les réglages d'un prochain firmware sont distingués de la carte
actuellement connectée.

**Chronogramme** affiche les trois signaux avec une largeur adaptée à la
fenêtre. Les exports SVG/CSV/VCD sont regroupés. **Journal** conserve les
commandes, réponses et messages ; la progression d'une compilation est
visible au-dessus des onglets, quelle que soit la vue choisie.

La construction des vues est extraite de `app.py` vers `ui_layout.py`.
Le contrôle du matériel reste dans `Studio` et le validateur des artefacts
est partagé entre téléchargement et chargement.

## Validation et limites

- **436 tests Python passent** après correction, dont les cas de STOP pendant
  compilation, INFO expiré, firmware inconnu, métadonnées altérées, NaN/Inf,
  rapports absents, ZIP dupliqué et les contraintes des 32 horloges.
- Ruff, formatage et mypy passent sur les 15 modules Python.
- Les cinq bancs RTL passent : 1 124 018 contrôles moteur, 42 cas ODDR,
  38 cas protocole, carte/UART et boucle UART à 200 MHz / 115200 bauds.
- Prévisualisation Flet 0.28.3 dans Chromium à **1220 × 930** et **760 × 680** :
  boutons visibles, SEND/STOP en démo, saisie invalide refusée, fréquence
  demandée de 15 MHz ramenée à 14,28571 MHz, chronogramme redimensionné,
  panneaux avancés et export réel du journal ; aucune exception JavaScript.

Les sources RTL, le XDC de référence et le `.bit` de Claude restent identiques.
Le firmware fourni conserve le SHA256
`859ad3674bcd2505c6f510436a5f123c3004f208be9fde969338a82e8f47effb`,
la graine 4 et la Fmax **206,14306640625 MHz**. Les modifications Python
ne nécessitent donc pas de remplacer ce firmware sur une carte déjà configurée
avec cette version. Les contraintes personnalisées corrigées s'appliquent
aux prochaines compilations.

La marge de routage est d'environ **3 %**. Aucune carte n'est raccordée ici :
ces résultats ne confirment ni le chargement physique ni les marges
CLK/DATA/LATCH à 200 MHz sur Pmod. Commencer les essais à fréquence réduite
et mesurer les signaux et les marges du récepteur avant de monter la fréquence.

## Améliorations suivantes proposées

1. **Validation sur carte** : documenter chargement SRAM, PING/INFO, LED et
   mesures CLK/DATA/LATCH sur plusieurs fréquences et polarités.
2. **Marge RTL à 200 MHz** : examiner les chemins du moteur dominés par le
   routage avant une nouvelle modification ; accepter uniquement un build
   qui passe le timing et republier son manifeste.
3. **Annulation de compilation** : ajouter une action explicite pour arrêter
   le suivi ou annuler une exécution GitHub sans perturber la liaison UART.
4. **Profils de firmware connus** : permettre leur import pour afficher le
   brochage d'un firmware personnalisé déjà chargé après redémarrage de l'app.

Ces propositions restent distinctes des corrections réalisées et testées ici.
